## Lernziele

Nach dieser Übung kannst du

- Indizes zur Beschleunigung von Abfragen anlegen
- den Ausführungsplan einer Abfrage mittels `EXPLAIN` grob analysieren

## Voraussetzungen

- Modul 5 (Daten aus Modul 4, darunter der Mitarbeiter Müller)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Index** | zusätzliche Datenstruktur, die den Zugriff auf Zeilen beschleunigt (in PostgreSQL standardmäßig ein B-Baum) |
| **B-Tree** | sortierter Baum; effizient für `=`, `<`, `>`, `BETWEEN` und `LIKE 'abc%'` |
| **Seq Scan** | liest die ganze Tabelle |
| **Index Scan / Bitmap Index Scan** | Zugriff über den Index; der Planer wählt je nach Statistik |
| **`EXPLAIN`** | zeigt den geplanten Ablauf einer Abfrage mit geschätzten Kosten und Zeilen |
| **`EXPLAIN ANALYZE`** | führt die Abfrage aus und zeigt zusätzlich tatsächliche Zeilen und Zeiten |
| **`ANALYZE`** | aktualisiert die Statistik, die der Planer für seine Entscheidungen verwendet |
| **Selektivität** | Anteil der Zeilen, die eine Bedingung liefert; Indizes lohnen sich bei hoher Selektivität (wenige Treffer) |

## Aufgabe

### Aufgabe 1 – Testdaten erzeugen (Einheit 10.1)

Mit nur wenigen Zeilen wählt PostgreSQL immer einen Sequential Scan; ein Index bringt dort nichts. Erzeuge daher 100000 Testzeilen und aktualisiere die Statistik:
```sql
INSERT INTO mitarbeiter (vorname, nachname, email, gehalt, abteilung_id)
SELECT 'Test' || g, 'Name' || (g % 5000), 'test' || g || '@example.com',
       2000 + (g % 3000), (SELECT MIN(abteilung_id) FROM abteilung)
FROM generate_series(1, 100000) AS g;
ANALYZE mitarbeiter;
```

### Aufgabe 2 – Baseline messen (Einheit 10.3)

Nutze `EXPLAIN ANALYZE SELECT * FROM mitarbeiter WHERE nachname = 'Müller';` und dokumentiere den Plan (erwartet: "Seq Scan") und die `Execution Time`.

### Aufgabe 3 – Index erstellen (Einheit 10.2)

Erstelle einen Index auf die Spalte Nachname (`CREATE INDEX idx_mitarbeiter_nachname ON mitarbeiter(nachname);`).

*Ergänzung der Ausarbeitung (Einheit 10.1):* Lies mit `SELECT pg_size_pretty(pg_relation_size('mitarbeiter')) AS tabelle, pg_size_pretty(pg_relation_size('idx_mitarbeiter_nachname')) AS index_nachname;` die Größen von Tabelle und Index und erkläre, was der Index zusätzlich belegt. Prüfe außerdem mit `EXPLAIN SELECT * FROM mitarbeiter WHERE nachname LIKE '%üller';`, ob der B-Tree-Index bei einem führenden Platzhalter genutzt wird, und mit `WHERE UPPER(nachname) = 'MÜLLER'`, ob er bei einer Funktion auf der Spalte genutzt wird.

### Aufgabe 4 – Vergleich (Einheit 10.3)

Führe das `EXPLAIN ANALYZE`-Kommando aus Aufgabe 2 erneut aus. Prüfe, ob nun ein "Index Scan" oder "Bitmap Index Scan" anstelle des "Seq Scan" verwendet wird (in einer Testumgebung mit PostgreSQL 16 erschien ein Bitmap Index Scan; welche Variante der Planer wählt, hängt von der Statistik ab), und vergleiche die `Execution Time`.

### Aufgabe 5 – Rückbau (Einheit 10.2)

Prüfe mit `SELECT COUNT(*) FROM mitarbeiter WHERE vorname LIKE 'Test%';`, dass genau 100000 Testzeilen vorhanden sind, und lösche sie mit `DELETE FROM mitarbeiter WHERE vorname LIKE 'Test%';`. Entferne danach den Index mit `DROP INDEX idx_mitarbeiter_nachname;` und prüfe, dass wieder nur die ursprünglichen Mitarbeiter vorhanden sind.

## Hinweise

- Bei wenigen Zeilen wählt der Planer immer einen Seq Scan; deshalb die 100 000 Testzeilen. Ohne `ANALYZE` kann die Statistik veraltet sein.
- Im Test fiel die Ausführungszeit von 5,3 ms (Seq Scan) auf 0,16 ms (Bitmap Index Scan). Deine Zeiten weichen ab; vergleiche das **Verhältnis** und die Planart, nicht den Absolutwert.
- Statt `Index Scan` erschien im Test ein **Bitmap Index Scan**; welche Variante der Planer wählt, hängt von der Statistik ab.
- Auffällig im Plan: Der Planer schätzte `rows=20`, tatsächlich gab es 1 Zeile; Schätzung und Wirklichkeit weichen bei ungleich verteilten Werten oft ab.
- Der Rückbau löscht die Testzeilen, aber der **Speicherplatz** der Tabelle bleibt zunächst belegt (im Test 9000 kB nach `DELETE`); `VACUUM` gibt ihn für die Wiederverwendung frei.
- Die IDs laufen nach dem Test weiter (die Zählfolge wird nicht zurückgesetzt): der nächste neue Mitarbeiter hat im Test die ID 100008.

## Kontrollfragen

1. Warum sollte man nicht einfach auf jede Spalte einer Tabelle einen Index legen?
2. Welchen Einfluss hat ein Index auf DML-Operationen (`INSERT`, `UPDATE`, `DELETE`)?
3. Was zeigt der Befehl `EXPLAIN` in PostgreSQL?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Testdaten erzeugen).** Die Testzeilen kommen aus dem Befehl der Aufgabe. Ergebnis (echte Ausgabe): `INSERT 0 100000`, danach `SELECT COUNT(*)` = 100006 (6 echte Mitarbeiter + 100 000 Testzeilen).

**Aufgabe 2 (Baseline messen).**

```text
EXPLAIN ANALYZE SELECT * FROM mitarbeiter WHERE nachname = 'Müller';
 Seq Scan on mitarbeiter  (cost=0.00..2375.07 rows=20 width=55) (actual time=0.007..5.300 rows=1 loops=1)
   Filter: ((nachname)::text = 'Müller'::text)
   Rows Removed by Filter: 100005
 Execution Time: 5.314 ms
```

**Aufgabe 3 (Index erstellen).**

```sql
CREATE INDEX idx_mitarbeiter_nachname ON mitarbeiter(nachname);
```

Der Index belegte im Test 816 kB bei 9000 kB Tabelle. **Ergänzung (Einheit 10.1, echte Ausgabe):** `LIKE '%üller'` und `UPPER(nachname) = 'MÜLLER'` verwenden den Index **nicht** (Seq Scan), weil der B-Baum nach dem Anfang des Werts sortiert ist bzw. die Funktion die Spalte verdeckt.

**Aufgabe 4 (Vergleich).**

```text
 Bitmap Heap Scan on mitarbeiter  (cost=4.45..76.70 rows=20 width=55) (actual time=0.139..0.140 rows=1 loops=1)
   ->  Bitmap Index Scan on idx_mitarbeiter_nachname  (cost=0.00..4.44 rows=20 width=0)
 Execution Time: 0.160 ms
```

Ausführungszeit: 5,3 ms → 0,16 ms (Faktor etwa 33).

**Aufgabe 5 (Rückbau).**

```text
SELECT COUNT(*) FROM mitarbeiter WHERE vorname LIKE 'Test%';     -- 100000
DELETE FROM mitarbeiter WHERE vorname LIKE 'Test%';              -- DELETE 100000
DROP INDEX idx_mitarbeiter_nachname;
SELECT COUNT(*) FROM mitarbeiter;                                -- 6
```

Übrig bleiben die ursprünglichen Mitarbeiter (im Test die IDs 1 bis 5 und 7).

**Fragen.** (1) Jeder Index belegt **Speicher** und muss bei Änderungen mitgepflegt werden (im Test 816 kB zusätzlich bei einer einzigen Spalte). Er lohnt sich nur für Spalten, die häufig in `WHERE`, `JOIN` oder `ORDER BY` stehen und selektiv sind; auf jede Spalte hilft er kaum und bremst das Schreiben. (2) Jede Änderung (`INSERT`, `DELETE`, `UPDATE` indizierter Spalten) muss die Indizes mitpflegen, daher werden Schreibvorgänge **langsamer**. Messung im Test: 300 000 Zeilen in eine temporäre Tabelle ohne Index 103 ms, mit Index auf `nachname` 711 ms (`beispiele/m10b.txt`; rechnerabhängig). (3) `EXPLAIN` zeigt den **Ausführungsplan**: welche Zugriffsmethoden (Seq Scan, Index Scan …), in welcher Reihenfolge und mit welchen geschätzten Kosten und Zeilenzahlen, ohne die Abfrage auszuführen. `EXPLAIN ANALYZE` führt sie aus und zeigt die tatsächlichen Werte.

</details>

## Erweiterungen

- Lege einen Index auf `gehalt` an und prüfe `WHERE gehalt > 4400` gegen `WHERE gehalt > 2100` (Selektivität).
- Probiere `CREATE INDEX … ON mitarbeiter (lower(nachname))` und eine Abfrage mit `lower(nachname) = 'müller'` (Funktionsindex).
- Miss mit `\timing`, wie viel länger ein `INSERT` von 300 000 Zeilen mit Index dauert (die Musterlösung nennt ein Beispiel).
