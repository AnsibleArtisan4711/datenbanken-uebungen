## Lernziele

Nach dieser Übung kannst du

- Datensätze manuell einfügen
- bestehende Daten sicher aktualisieren
- Daten selektiv löschen, ohne unbeabsichtigt den gesamten Bestand zu entfernen

## Voraussetzungen

- Modul 3 (die Tabellen `abteilung`, `mitarbeiter` und `projekt` existieren)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **DML** | Data Manipulation Language: `INSERT`, `UPDATE`, `DELETE` |
| **`INSERT … VALUES`** | fügt Zeilen ein; Spaltenliste angeben |
| **`RETURNING`** | gibt Spalten der eingefügten oder geänderten Zeilen zurück (PostgreSQL), z. B. die vergebene ID |
| **`WHERE`** | wählt die betroffenen Zeilen; ohne `WHERE` sind **alle** betroffen |
| **Auto-Commit** | jede Anweisung wird sofort fest gespeichert und kann nicht zurückgenommen werden |
| **Referenzielle Integrität** | Fremdschlüssel verhindern Verweise ins Leere und das Löschen referenzierter Zeilen |
| **`NULL`** | fehlender oder unbekannter Wert; nicht gleich Null oder leerer Text |

## Aufgabe

### Aufgabe 1 – INSERT (Einheit 4.1)

Füge 3 Abteilungen (z. B. Verwaltung, Technik, Vertrieb) in die Tabelle `abteilung` ein und ermittle die vergebenen IDs mit `SELECT`. Füge anschließend 5 fiktive Mitarbeiter (E-Mail-Adressen mit `example.com`) in die Tabelle `mitarbeiter` ein, jeweils mit Gehalt und unterschiedlichem `einstellungsdatum`. Achte auf die Foreign-Key-Abhängigkeiten (zuerst Abteilung, dann Mitarbeiter anlegen). Die Daten müssen diese Bedingungen erfüllen, weil spätere Module sie brauchen: ein Mitarbeiter heißt Müller, mindestens zwei Nachnamen beginnen mit „M“, drei Mitarbeiter gehören zur selben Abteilung, ein Mitarbeiter hat keine E-Mail-Adresse (`NULL`), jeder Mitarbeiter hat eine Abteilung. Füge außerdem 2 Projekte in `projekt` ein. Speichere alle `INSERT`-Anweisungen in einem DBeaver-Skript `02_daten.sql`.

### Aufgabe 2 – UPDATE (Einheit 4.2)

Erhöhe das Gehalt des Mitarbeiters Müller mithilfe einer `WHERE`-Klausel, die den Primärschlüssel anspricht. Prüfe mit `SELECT` vorher und nachher den Wert.

### Aufgabe 3 – DELETE mit Prüfpunkt (Einheit 4.3)

Füge zunächst einen Testmitarbeiter (Vorname `Test`, Nachname `Löschkandidat`) ein und ermittle seine ID. Prüfe mit `SELECT COUNT(*) FROM mitarbeiter` die Zeilenzahl. DBeaver führt Änderungen standardmäßig sofort fest aus (Auto-Commit, nicht bestätigt); ein `DELETE` ist daher nicht zurücknehmbar, der Bestand lässt sich nur mit dem Skript `02_daten.sql` neu einfügen. Lösche genau diesen Testmitarbeiter anhand seiner ID und prüfe die Zeilenzahl erneut. Versuche dann ein `DELETE` auf eine Abteilung, die noch Mitarbeiter hat, um den Foreign-Key-Constraint-Fehler zu provozieren (Meldung `violates foreign key constraint`).

## Hinweise

- Reihenfolge beim Einfügen: zuerst `abteilung`, dann `mitarbeiter` und `projekt` (Fremdschlüssel).
- Die Beispieldaten erfüllen die Bedingungen der Aufgabe: Müller, mit Maier zwei Nachnamen mit „M“, drei Mitarbeiter in Technik, Berger ohne E-Mail, jeder Mitarbeiter hat eine Abteilung. Eigene Daten dürfen abweichen, **müssen** diese Bedingungen aber erfüllen.
- Nimm die ID des Testmitarbeiters aus `INSERT … RETURNING mitarbeiter_id` oder aus einem `SELECT`; setze sie nicht aus der Erinnerung ein. In der Testumgebung war es die 6; mit Lücken in den IDs (siehe Modul 3) hätte es eine andere sein können.
- Das Skript `02_daten.sql` funktioniert nur auf **leeren** Tabellen; auf vorhandenen Daten scheitert es an der `UNIQUE`-Bedingung der E-Mail-Adresse oder erzeugt doppelte Zeilen.
- Die Erhöhung des Gehalts in Aufgabe 2 war im Test **5 %** (`gehalt * 1.05`, Müller: 3800,00 auf 3990,00); spätere Beispielausgaben dieser Reihe rechnen mit diesem Wert.

## Kontrollfragen

1. Wofür steht DML?
2. Warum sollte ein `UPDATE`- oder `DELETE`-Befehl im produktiven Einsatz fast immer eine `WHERE`-Klausel enthalten?
3. Was passiert, wenn man einen Datensatz löschen möchte, auf den noch ein Fremdschlüssel aus einer anderen Tabelle verweist (Standardverhalten ohne CASCADE)?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (INSERT).** Das Skript `02_daten.sql` (siehe Dateien dieser Übung) enthält die `INSERT`-Anweisungen. Ergebnis (echte Ausgabe, Auszug):

```text
 abteilung_id |    name    | standort
--------------+------------+----------
            1 | Verwaltung | Wien
            2 | Technik    | Linz
            3 | Vertrieb   | Graz
 mitarbeiter_id | vorname | nachname |           email           | gehalt  | abteilung_id
----------------+---------+----------+---------------------------+---------+--------------
              1 | Anna    | Müller   | anna.mueller@example.com  | 3800.00 |            2
              2 | Peter   | Maier    | peter.maier@example.com   | 4200.00 |            2
              3 | Karl    | Huber    | karl.huber@example.com    | 3600.00 |            2
              4 | Eva     | Berger   |                           | 3100.00 |            1
              5 | Lukas   | Steiner  | lukas.steiner@example.com | 4500.00 |            3
```

**Aufgabe 2 (UPDATE).**

```sql
SELECT mitarbeiter_id, nachname, gehalt FROM mitarbeiter WHERE mitarbeiter_id = 1;   -- 3800.00
UPDATE mitarbeiter SET gehalt = gehalt * 1.05 WHERE mitarbeiter_id = 1;               -- UPDATE 1
SELECT mitarbeiter_id, nachname, gehalt FROM mitarbeiter WHERE mitarbeiter_id = 1;   -- 3990.00
```

Die ID des Mitarbeiters Müller ist im Test 1; in deiner Datenbank per `SELECT` nachsehen. **Ergänzung (echt ausgeführt):** Ein `UPDATE` ohne `WHERE` (`UPDATE mitarbeiter SET gehalt = 1;`) änderte alle Zeilen (`UPDATE 5`); im Test stand es in einer Transaktion und wurde mit `ROLLBACK` zurückgenommen, im Auto-Commit wäre es endgültig.

**Aufgabe 3 (DELETE mit Prüfpunkt).**

```text
INSERT INTO mitarbeiter (vorname, nachname, abteilung_id) VALUES ('Test', 'Löschkandidat', 1) RETURNING mitarbeiter_id;
 mitarbeiter_id
----------------
              6
SELECT COUNT(*) FROM mitarbeiter;     -- 6
DELETE FROM mitarbeiter WHERE mitarbeiter_id = 6;   -- DELETE 1
SELECT COUNT(*) FROM mitarbeiter;     -- 5
DELETE FROM abteilung WHERE abteilung_id = 2;
ERROR:  update or delete on table "abteilung" violates foreign key constraint "fk_mitarbeiter_abteilung" on table "mitarbeiter"
DETAIL:  Key (abteilung_id)=(2) is still referenced from table "mitarbeiter".
```

**Fragen.** (1) DML steht für **Data Manipulation Language** (Datenmanipulation): `INSERT`, `UPDATE`, `DELETE` (häufig wird auch `SELECT` dazugezählt). (2) Ohne `WHERE` wirkt der Befehl auf **alle** Zeilen der Tabelle. Im Test setzte `UPDATE mitarbeiter SET gehalt = 1` alle fünf Gehälter auf 1,00 (hier per `ROLLBACK` zurückgenommen); im Auto-Commit wäre die Änderung sofort endgültig, und ein `DELETE` ohne `WHERE` leert die Tabelle. (3) Im Standardverhalten (ohne `CASCADE`, also `NO ACTION`) **schlägt das `DELETE` mit einem Fehler fehl** (`violates foreign key constraint`, im Test für die Abteilung Technik); die Datenbank schützt so vor Verweisen ins Leere. Mit `ON DELETE CASCADE` würden die abhängigen Zeilen mitgelöscht, mit `ON DELETE SET NULL` der Verweis geleert.

</details>

## Erweiterungen

- Füge mit einem einzigen `INSERT` mehrere Zeilen ein und vergleiche mit mehreren einzelnen Anweisungen.
- Lege den Fremdschlüssel `fk_projekt_abteilung` mit `ON DELETE CASCADE` neu an und beobachte, was beim Löschen einer Abteilung mit Projekten passiert (nur in einer Kopie der Datenbank).
- Probiere `INSERT … ON CONFLICT (email) DO NOTHING` mit einer doppelten E-Mail aus.
