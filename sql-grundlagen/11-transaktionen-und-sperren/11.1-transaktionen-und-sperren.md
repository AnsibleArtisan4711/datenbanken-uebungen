## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **ACID** | Atomicity (alles oder nichts), Consistency (gültiger Zustand), Isolation (Transaktionen stören sich nicht), Durability (Dauerhaftigkeit) |
| **Transaktion** | Folge von Anweisungen, die als Einheit gilt (`BEGIN` … `COMMIT` oder `ROLLBACK`) |
| **`ROLLBACK`** | verwirft alle Änderungen der laufenden Transaktion |
| **Isolationsstufe `READ COMMITTED`** | Standard in PostgreSQL: eine Abfrage sieht nur bereits bestätigte Änderungen anderer Transaktionen |
| **Row Lock** | Sperre auf einer geänderten Zeile bis zum Ende der Transaktion |
| **Deadlock** | zwei Transaktionen warten gegenseitig auf Sperren der jeweils anderen; PostgreSQL bricht eine ab |
| **`OVERRIDING SYSTEM VALUE`** | erlaubt eigene Werte für `GENERATED ALWAYS`-Spalten beim Einfügen |

## Aufgabe

### Aufgabe 1 – Sicherung anlegen (Einheit 11.2)

Lege vor den Übungen eine Sicherungskopie an: `CREATE TABLE mitarbeiter_sicherung AS SELECT * FROM mitarbeiter;` und prüfe die Zeilenzahl beider Tabellen. DBeaver führt Änderungen standardmäßig sofort fest aus (nicht bestätigt); stelle für die folgenden Aufgaben den Transaktionsmodus auf „Manuell“ (Bezeichnung und Ort nicht bestätigt) und beende jede Transaktion ausdrücklich mit `COMMIT` oder `ROLLBACK`. Sollten Daten verloren gehen, stellst du sie mit `DELETE FROM mitarbeiter;` und `INSERT INTO mitarbeiter OVERRIDING SYSTEM VALUE SELECT * FROM mitarbeiter_sicherung;` wieder her.

### Aufgabe 2 – Rollback testen (Einheit 11.1, Einheit 11.2)

Öffne ein SQL-Skript. Starte eine Transaktion mit `BEGIN;`. Lösche per `DELETE` alle Datensätze der Mitarbeitertabelle. Mache einen `SELECT` (Tabelle ist leer). Setze ein `ROLLBACK;` ab. Prüfe per `SELECT`, ob die Daten wieder da sind.

### Aufgabe 3 – Commit (Einheit 11.2)

Starte eine Transaktion (`BEGIN;`), füge einen Datensatz hinzu und bestätige diese permanent mit `COMMIT;`.

### Aufgabe 4 – Locks und Isolation (Einheit 11.1, Einheit 11.3)

Öffne **zwei** unabhängige Verbindungen (zwei SQL-Editor-Tabs; legt DBeaver für den zweiten Tab keine eigene Verbindung an, erstelle eine zweite Verbindung `firma-2`; nicht bestätigt). Starte in Tab 1 `BEGIN;` und ändere eine Zeile (UPDATE), mach aber *kein* COMMIT. Lies in Tab 2 dieselbe Zeile per `SELECT` (sie zeigt noch den alten Wert; Standard-Isolation `READ COMMITTED`). Versuche in Tab 2 dieselbe Zeile per UPDATE zu ändern. Beobachte, wie Tab 2 "hängt", bis Tab 1 ein `COMMIT` oder `ROLLBACK` durchführt.

### Aufgabe 5 – Deadlock provozieren (Einheit 11.3)

Starte in Tab 1 `BEGIN;` und ändere die Zeile mit `mitarbeiter_id = 1`; starte in Tab 2 `BEGIN;` und ändere die Zeile mit `mitarbeiter_id = 2`. Ändere dann in Tab 1 die Zeile 2 (Tab 1 wartet) und in Tab 2 die Zeile 1. PostgreSQL erkennt den Deadlock nach kurzer Zeit und bricht eine der beiden Transaktionen mit `ERROR: deadlock detected` ab. Beende beide Transaktionen mit `ROLLBACK;`.

### Aufgabe 6 – Rückbau (Einheit 11.2)

Prüfe, dass `mitarbeiter` und `mitarbeiter_sicherung` wieder dieselbe Anzahl Zeilen haben (abgesehen vom Datensatz aus Aufgabe 3), und lösche die Sicherung mit `DROP TABLE mitarbeiter_sicherung;`.

## Hinweise

- `psql` und DBeaver führen Anweisungen standardmäßig sofort fest aus (Auto-Commit; für DBeaver nicht bestätigt). Mit `BEGIN;` beginnt eine explizite Transaktion, die bis `COMMIT;` oder `ROLLBACK;` gilt.
- Nach einem Fehler in einer Transaktion sind alle weiteren Befehle gesperrt (`current transaction is aborted, commands ignored until end of transaction block`); nur `ROLLBACK` hilft (Test mit `SELECT 1/0`).
- **Aufgabe 4 und 5 brauchen zwei gleichzeitige Verbindungen.** Der Ausgang von Aufgabe 5 hängt vom Zeitpunkt ab: PostgreSQL bricht **eine** der beiden Transaktionen nach `deadlock_timeout` (Standard 1 Sekunde, Fachwissen) ab; welche, ist nicht vorhersagbar (im Test traf es Sitzung A).
- Die IDs 1 und 2 aus Aufgabe 5 müssen vorhanden sein (im Test Müller und Maier); prüfe sie mit `SELECT` und passe sie sonst an.
- **Ergänzung der Ausarbeitung:** Aufgabe 4 ändert Müllers Gehalt (im Test +100 und +50). Setze es danach auf den Wert vorher zurück (im Test 3990,00), damit spätere Ausgaben stimmen.
- `CREATE TABLE … AS SELECT` kopiert Daten, aber **keine** Constraints, keinen Primärschlüssel und keine Identity-Eigenschaft. Das Zurückspielen mit `OVERRIDING SYSTEM VALUE` setzt voraus, dass die Spaltenreihenfolge gleich ist (hier gegeben).
- Der Test nutzt `pg_sleep`, um Sitzung A die Transaktion offen halten zu lassen; im Kurs hältst du sie von Hand offen.

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Sicherung anlegen).**

```text
CREATE TABLE mitarbeiter_sicherung AS SELECT * FROM mitarbeiter;
 original | sicherung
----------+-----------
        6 |         6
```

Die Sicherung enthält die Daten, aber keine Schlüssel und Constraints (`\d mitarbeiter_sicherung`). **Ergänzung (echt ausgeführt, in Transaktion zurückgerollt):** `DELETE FROM mitarbeiter; INSERT INTO mitarbeiter OVERRIDING SYSTEM VALUE SELECT * FROM mitarbeiter_sicherung;` stellte alle Zeilen wieder her.

**Aufgabe 2 (Rollback testen).**

```text
BEGIN;  DELETE FROM mitarbeiter;     -- DELETE 6
SELECT COUNT(*) FROM mitarbeiter;     -- 0
ROLLBACK;
SELECT COUNT(*) FROM mitarbeiter;     -- 6
```

**Aufgabe 3 (Commit).**

```sql
BEGIN;
INSERT INTO mitarbeiter (vorname, nachname, email, gehalt, abteilung_id) VALUES ('Tina', 'Wagner', 'tina.wagner@example.com', 3400.00, 3) RETURNING mitarbeiter_id;
COMMIT;
```

Im Test erhielt Wagner die ID 100008 (die Zählfolge lief nach Modul 10 weiter). Danach hat `mitarbeiter` sieben Zeilen. **Ergänzung (echte Ausgabe):** Ein Fehler in einer Transaktion (`SELECT 1/0`) sperrt die Transaktion bis zum `ROLLBACK`.

**Aufgabe 4 (Locks und Isolation).** Zeitlicher Ablauf im Test (Sitzung A = Tab 1, B = Tab 2, C = Beobachter):

```text
A: BEGIN; UPDATE mitarbeiter SET gehalt = gehalt + 100 WHERE mitarbeiter_id = 1;  (kein COMMIT)
B: SELECT nachname, gehalt FROM mitarbeiter WHERE mitarbeiter_id = 1;     -- Müller 3990.00 (alter Wert)
B: UPDATE mitarbeiter SET gehalt = gehalt + 50 WHERE mitarbeiter_id = 1;  -- hängt
C: SELECT pid, state, wait_event_type, wait_event … FROM pg_stat_activity …
   <pid B> | active | Lock | transactionid | UPDATE mitarbeiter SET gehalt = gehalt + 50 …
   pg_blocking_pids(<pid B>) = {<pid A>}          (Prozessnummern ändern sich bei jedem Lauf)
A: COMMIT;                                                         -- B läuft weiter
B: UPDATE 1  (Wartezeit im Test ca. 4,5 s)    SELECT … → 4140.00  (3990 + 100 + 50)
```

Sitzung B las den alten Wert (`READ COMMITTED`: ungesicherte Änderungen sind unsichtbar) und wartete beim `UPDATE` auf die Zeilensperre; nach dem `COMMIT` rechnete sie auf dem **neuen** Wert weiter.

**Aufgabe 5 (Deadlock provozieren).**

```text
A: BEGIN; UPDATE … WHERE mitarbeiter_id = 1; pg_sleep(2);
B: BEGIN; UPDATE … WHERE mitarbeiter_id = 2; pg_sleep(2);
A: UPDATE … WHERE mitarbeiter_id = 2;   B: UPDATE … WHERE mitarbeiter_id = 1;
A: ERROR:  deadlock detected
   DETAIL:  Process <A> waits for ShareLock on transaction <x>; blocked by process <B>.
   Process <B> waits for ShareLock on transaction <y>; blocked by process <A>.
   HINT:  See server log for query details.
```

Eine der beiden Sitzungen wird abgebrochen (hier A), die andere läuft durch; beide Transaktionen mit `ROLLBACK;` beenden.

**Aufgabe 6 (Rückbau).** Müllers Gehalt zurücksetzen (`UPDATE mitarbeiter SET gehalt = 3990.00 WHERE mitarbeiter_id = 1;`, im Test 3990,00). Dann `mitarbeiter` 7 Zeilen, `mitarbeiter_sicherung` 6 (der Unterschied ist Wagner aus Aufgabe 3); `DROP TABLE mitarbeiter_sicherung;`.

**Fragen.** (1) **A**tomicity (Atomarität: alles oder nichts), **C**onsistency (Konsistenz: die Datenbank bleibt gültig, Constraints gelten), **I**solation (Transaktionen beeinflussen sich nicht), **D**urability (Dauerhaftigkeit: bestätigte Änderungen überstehen einen Absturz). (2) `ROLLBACK;` (3) Ein **Deadlock** (Verklemmung): PostgreSQL erkennt ihn nach kurzer Zeit und bricht eine der beteiligten Transaktionen mit `ERROR: deadlock detected` ab.

</details>
