## Lernziele

Nach dieser Übung kannst du

- Datenbank-Sichten anlegen und abfragen
- den Unterschied zwischen logischen Views und Materialized Views (PostgreSQL-spezifisch) erklären

## Voraussetzungen

- Modul 7

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **View (Sicht)** | gespeicherte Abfrage mit eigenem Namen; verhält sich wie eine Tabelle |
| **`CREATE VIEW` / `DROP VIEW`** | legt eine Sicht an bzw. entfernt sie |
| **Materialized View** | speichert das **Ergebnis** der Abfrage physisch (PostgreSQL); wird mit `REFRESH MATERIALIZED VIEW` aktualisiert |
| **Abhängigkeit** | Views hängen von ihren Basistabellen ab; `DROP TABLE` scheitert, solange Views darauf verweisen |
| **Rechte auf Views** | `GRANT SELECT` auf die Sicht, nicht auf die Tabelle |
| **`CASCADE`** | löscht abhängige Objekte mit; mit Vorsicht verwenden |

## Aufgabe

### Aufgabe 1 – CREATE VIEW (Einheit 9.1, Einheit 9.2)

Erstelle eine Abfrage mit Join (`LEFT JOIN`, damit Mitarbeiter ohne Abteilung erhalten bleiben), die sensible Mitarbeiterdaten (wie Gehälter) ausblendet und nur Name, Abteilung und E-Mail anzeigt. Speichere dies als `VIEW vw_mitarbeiterliste`.

### Aufgabe 2 – View abfragen (Einheit 9.1)

Führe ein einfaches `SELECT * FROM vw_mitarbeiterliste` aus.

### Aufgabe 3 – Materialized View (Einheit 9.3)

Erstelle eine `MATERIALIZED VIEW` über eine aggregierte Statistik (z.B. Mitarbeiteranzahl pro Abteilung) und probiere den Befehl `REFRESH MATERIALIZED VIEW` aus, nachdem du einen Datensatz in der Basistabelle geändert hast.

### Aufgabe 4 – DROP VIEW (Einheit 9.2)

Entferne die View probeweise mit `DROP VIEW vw_mitarbeiterliste;` und lege sie mit dem Befehl aus Aufgabe 1 erneut an.

## Hinweise

- Der `LEFT JOIN` in der View ist nötig, damit Neumann (ohne Abteilung) erhalten bleibt: ein `INNER JOIN` würde ihn ausblenden.
- Eine normale View zeigt Änderungen der Basistabelle **sofort**; die Materialized View zeigt sie erst nach `REFRESH MATERIALIZED VIEW` (Test).
- **Ergänzung der Ausarbeitung:** Aufgabe 3 verändert vorübergehend Neumanns Abteilung (nach `Archiv`). Setze sie danach mit `UPDATE mitarbeiter SET abteilung_id = NULL WHERE nachname = 'Neumann';` zurück, damit die späteren Module denselben Bestand sehen.
- `DROP TABLE abteilung` scheitert, solange Views, Materialized Views oder Fremdschlüssel darauf verweisen (Test: Meldung mit vier abhängigen Objekten). Die Reihenfolge ist wichtig für spätere Aufräumarbeiten (Modul 12).
- Die Materialized View braucht Platz und wird bei Änderungen der Basistabelle **nicht** automatisch aktualisiert.

## Kontrollfragen

1. Speichert ein Standard-View die Daten physisch auf der Festplatte?
2. Warum nutzt man Sichten im Hinblick auf Sicherheit und Berechtigungsmanagement?
3. In welchem Szenario ist ein "Materialized View" einem Standard-View vorzuziehen?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (CREATE VIEW).**

```sql
CREATE VIEW vw_mitarbeiterliste AS
SELECT m.vorname, m.nachname, a.name AS abteilung, m.email
FROM mitarbeiter m LEFT JOIN abteilung a ON a.abteilung_id = m.abteilung_id;
```

Die View enthält kein `gehalt`. Ein Beispiel für die Rechte steht unter Aufgabe 2 und in `beispiele/m09b.txt`.

**Aufgabe 2 (View abfragen).**

```sql
SELECT * FROM vw_mitarbeiterliste ORDER BY nachname;
```

Ergebnis: sechs Zeilen, auch Neumann mit leerer Abteilung. **Ergänzung (echte Ausgabe):** Ändert man die E-Mail von Huber in der Tabelle, zeigt die View sie sofort. **Rechte (als Superuser `postgres`):** Nach `CREATE ROLE leser; GRANT SELECT ON vw_mitarbeiterliste TO leser;` liefert `SET ROLE leser; SELECT COUNT(*) FROM vw_mitarbeiterliste;` den Wert 6, während `SELECT gehalt FROM mitarbeiter;` mit `permission denied for table mitarbeiter` scheitert.

**Aufgabe 3 (Materialized View).**

```sql
CREATE MATERIALIZED VIEW mv_abteilung_statistik AS
SELECT a.name AS abteilung, COUNT(m.mitarbeiter_id) AS anzahl
FROM abteilung a LEFT JOIN mitarbeiter m ON m.abteilung_id = a.abteilung_id GROUP BY a.name;
UPDATE mitarbeiter SET abteilung_id = (SELECT abteilung_id FROM abteilung WHERE name = 'Archiv') WHERE nachname = 'Neumann';
SELECT * FROM mv_abteilung_statistik;     -- unverändert: Archiv 0
REFRESH MATERIALIZED VIEW mv_abteilung_statistik;
SELECT * FROM mv_abteilung_statistik;     -- Archiv 1
UPDATE mitarbeiter SET abteilung_id = NULL WHERE nachname = 'Neumann';     -- Ergänzung: zurücksetzen
```

**Aufgabe 4 (DROP VIEW).**

```text
DROP VIEW vw_mitarbeiterliste;
SELECT * FROM vw_mitarbeiterliste;
ERROR:  relation "vw_mitarbeiterliste" does not exist
CREATE VIEW vw_mitarbeiterliste AS …      (Befehl aus Aufgabe 1)
```

Danach liefert die View wieder sechs Zeilen. **Ergänzung (Abhängigkeiten):** `DROP TABLE abteilung;` scheitert mit `cannot drop table abteilung because other objects depend on it` (Fremdschlüssel, Materialized View, View).

**Fragen.** (1) **Nein.** Ein Standard-View speichert nur die Definition der Abfrage; die Daten werden bei jeder Abfrage aus den Basistabellen gelesen (im Test erschien eine Änderung sofort). Erst die Materialized View speichert das Ergebnis. (2) Eine View zeigt nur ausgewählte Spalten und Zeilen. Man gibt Benutzern Rechte auf die View statt auf die Tabelle und verbirgt so sensible Spalten (im Test: `leser` sieht die View, bekommt aber `permission denied` für `mitarbeiter` mit dem Gehalt). (3) Wenn die Abfrage **teuer** ist (große Aggregationen, viele Joins), die Daten sich selten ändern und leicht veraltete Werte akzeptabel sind (z. B. Berichte); das Ergebnis liegt fertig vor und wird schnell gelesen, muss aber mit `REFRESH` aktualisiert werden.

</details>

## Erweiterungen

- Lege eine Rolle `leser` an, erteile ihr `GRANT SELECT ON vw_mitarbeiterliste` und prüfe, dass `SELECT gehalt FROM mitarbeiter` für sie scheitert (die Musterlösung zeigt ein Beispiel).
- Probiere `CREATE OR REPLACE VIEW` mit einer zusätzlichen Spalte am Ende aus.
- Erstelle einen Index auf eine Materialized View und vergleiche mit der normalen View.
